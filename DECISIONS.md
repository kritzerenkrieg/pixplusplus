# Decisions

Source of truth: overrules `ARCHITECTURE.md` and `ROADMAP.md`. A code is the roadmap phase letter plus a sequence number. Codes are stable and never reused, and a new feature takes the next free letter. A phase starts only when its rows are Decided.

**Status:** **Decided**: binding, with the reason in a few words. **Inspect**: research or a spike first. **TBD**: ask, don't guess. **Question**: not yet read by the human, so treat it as TBD.

**Phases:** A Foundations (done), B Core solver and parity (done), C Controls and harness (done), D Benchmark run and report (done), E Post-benchmark features, G PixelOE in Rust, H PixelOE speed, I Any output size, J Native GUI, K Colour fidelity, L GUI profiles. Letter F is unused.

**Scope:** Pix++ only. The rows `C3`, `C4` and `D1`–`D4` were research work (benchmark design, verdict, raters) and are retired; their codes stay so old citations resolve.

## Current state (2026-11-17)

- **Methods (E8):** base PIA (default), PIA + importance map (`--importance FILE|auto`), PixelOE (`--method pixeloe`, to be ported).
- **Next work:** cut the edge weight (E1), format once (E4), `--importance auto` (E7), then the PixelOE port (Phase G, G1–G4).
- **Next work:** native GUI (Phase J, J1–J6), then colour fidelity (Phase K: K1, K2, K4).
- **Open:** none (2026-11-21).
- **Not now:** palette per material (E3). PIA solver stays as is (E5).

| G7 | PixelOE output size | Decided | `-s` means output size for both methods. | G8 | PixelOE palette | Decided | Under `--method pixeloe`, the image is quantised only when `-k N` is given (k-means, N colours). Without it, the output is unquantised like upstream's default. PIA still defaults to `-k 16`. User choice (2026-11-18). |

| G10 | PixelOE `-k` is a hard limit | Decided | Upstream runs `match_color(quantised, down)` after k-means, which brings back continuous tones (568 colours at `-k 16` on the smoke image). | Q5 | PixelOE k-means sums in f32 | Question | CodeRabbit (PR #1): `kmeans_step` sums each cluster in f32, which drifts on large flat areas (a constant 204/255 image at 512×512 gives a 203 centroid); torch sums pairwise and gets 204. Summing in f64 fixed that, and Linux and Windows agreed, but macOS then produced a different k-centroid image from the Linux reference (`pixeloe_kc_s48.png`, CI run 44865349120), so the change was reverted. Options: (a) f64 sums plus finding which step differs on macOS (likely a float-library call such as `powf` feeding a near-tie, G6); (b) pairwise f32 summation like torch; (c) leave it (only very large flat areas are affected). Since J5 dropped macOS, (a) needs no macOS work: f64 sums agreed on Linux and Windows. |
| Q1 | CI for multiplatform builds | Decided | A GitHub Actions workflow on Ubuntu and Windows (macOS dropped with J5, 2026-11-21) for every push and pull request: `cargo fmt --check`, `cargo clippy` with and without `gui`, `cargo test` (with `gui`), and release builds of the CLI and GUI. The Ubuntu runner installs the GTK dev packages for the native file dialogs. No binaries published. User choice (2026-11-21). |
| K1 | Palette by colour decimation | Decided | Opt-in `--palette decimate` for both methods (default palette unchanged). Repeatedly merge the closest pair of colours, keeping the heavier colour unchanged, then map each pixel to its nearest palette colour with no dither. PIA solves at a larger palette and decimates down to `-k`, so the solver is unchanged (E5); the compat path stays as is (A4, B1). Compare RGB (user proposal) against Oklab distance on several images before any default change. Evidence (smoke image, 128, k8): PIA top-5 % chroma 0.073 → 0.124, mean ΔE 4.6 → 5.7; PixelOE loses the dither pattern. User choice (2026-11-20). |
| K2 | PixelOE dither default | Decided | The GUI defaults to no dither; the CLI keeps upstream's ordered dither (G9). User choice (2026-11-20). |
| K3 | PIA saturation | Decided | Not now: PIA keeps the paper's 1.1 boost (B5). Decimation (K1, K5) and the saturation controls (K4) cover the dull-colour case; raise again as a new row if outputs still look dull. User choice (2026-11-21). |
| K4 | Saturation and contrast controls | Decided | Two separate adjustments, both in Oklab (chroma × saturation; lightness stretched by contrast around the image's mean lightness, so overall brightness stays put): a pre-adjust on the input before the palette is chosen, and a post-adjust on the final output, applied per colour so it never adds colours (`-k` stays a hard limit, G10). Both methods, all four in the GUI. Defaults are neutral (1.0) except post-saturation under PIA, which keeps 1.1 (B5). Flags (agent naming): `--pre-saturation`, `--pre-contrast`, `--saturation`, `--contrast`; `--saturation` now also works under PixelOE instead of being ignored. Compat path unchanged (A4, B1). User choice (2026-11-20). |
| K5 | Decimation distance: RGB or Oklab | Decided | Offer both, separately from native: `--palette native\|decimate-oklab\|decimate-rgb` (GUI: native, decimate (Oklab), decimate (RGB)); the default stays native. Profiles that saved the first build's `decimate` load as RGB. User choice (2026-11-21). Evidence: Measured on the 6 showcase images at 128 (`examples/decimate_compare.rs`; mean ΔE in Oklab ×100 against a box-downscaled source; chroma kept = output vs source): PIA k8 native 4.82 / RGB 5.26 / Oklab 5.06, top-5 % chroma kept 88 % / 90 % / 99 %; PIA k16 3.98 / 3.97 / 3.92; PixelOE k8 7.42 / 7.62 / 7.41, top-5 % chroma 79 % / 110 % / 96 %; PixelOE k16 6.99 / 6.82 / 6.62. Oklab has the lowest error in all four cases. By eye, RGB keeps the most vivid colours but scatters stray bright pixels (orange specks on land_castle, odd blues on toon_chibi), and it loses toon_chibi's red hat and blue hair at k8, which Oklab keeps. Agent recommends Oklab for `--palette decimate`; RGB could stay available as `--palette decimate-rgb` if wanted. Decimating PIA costs about 3× the time (1.1 s → 3.3 s at 128, from the 64-colour solve). |
| Q2 | `--importance auto` on very tall or wide images | Decided | Cap the saliency working image at 512 tall. Only inputs more than 8× taller than wide get a coarser map; every other image keeps its exact, harness-identical map (E7). Background: CodeRabbit (PR #1) found tall, narrow inputs make the direct DFT quadratic (8×1024 → 64×8192, minutes). User choice (2026-11-21). |
| Q3 | PixelOE padding grows both axes | Decided | Keep upstream's behaviour for parity (G3, G5): when one axis needs padding, both gain an output cell. Only reachable with `--input-factor 0`; documented in `docs/PORTING.md`. User choice (2026-11-21). |
